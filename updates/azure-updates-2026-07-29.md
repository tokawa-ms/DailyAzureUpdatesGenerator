### 2. Generally Available: NAT64 on StandardV2 NAT Gateway

**公開日時**: 2026年07月28日 18:50:11 UTC
**リンク**: [Generally Available: NAT64 on StandardV2 NAT Gateway](https://azure.microsoft.com/updates?id=568409)

**アップデートID**: 568409
**情報源**: Azure Updates API

**カテゴリ**: Launched, Networking, Azure NAT Gateway, Services, Feature

**要約**:

【何が更新されたか】  
AzureのStandardV2 NAT Gatewayで「NAT64」機能が一般提供（GA）されました。

【主な変更点や新機能】  
NAT64のサポートにより、IPv6ワークロードがIPv4のみのインターネット宛先と通信可能になりました。これは、合成されたアウトバウンドIPv6トラフィックをIPv4トラフィックへ変換することで実現されます。NAT64の動作には、DNS64対応のリゾルバーが必要です。

【影響を受ける対象】  
IPv6アドレスを利用するアプリケーションやワークロードをAzure上で運用している技術者や企業が対象です。特に、IPv6からIPv4のみ対応の外部サービスやインターネットへの接続が必要な場合に有効です。

【注意点】  
NAT64機能の利用にはDNS64対応リゾルバーが必須です。既存のNAT Gateway設定やDNS構成を確認し、必要に応じてDNS64リゾルバーを導入してください。また、IPv6とIPv4間の通信に関するセキュリティや運用ポリシーも再確認することを推奨します。

**詳細**:

今回のアップデートでは、AzureのStandardV2 NAT GatewayにNAT64機能が一般提供（GA）されました。NAT64の導入背景としては、IPv6対応ワークロードが増加する中で、依然として多くのインターネットサービスがIPv4のみで提供されている現状があります。これにより、IPv6環境で稼働するアプリケーションやサービスがIPv4のみの宛先と通信する必要性が高まっています。NAT64の提供は、こうした課題を解決し、Azure上でのIPv6ワークロードの柔軟な運用を可能にすることを目的としています。

具体的な機能として、StandardV2 NAT GatewayがNAT64をサポートすることで、アウトバウンドのIPv6トラフィックをIPv4トラフィックへ変換できるようになります。これにより、IPv6アドレスを持つ仮想マシンやサービスが、IPv4のみのインターネット宛先とシームレスに通信できます。NAT64の動作にはDNS64対応のリゾルバーが必要となります。DNS64は、IPv4アドレスしか持たない宛先に対して、合成されたIPv6アドレスを生成し、クライアントがIPv6で通信できるようにします。NAT64はこの合成されたIPv6アドレスを受け取り、実際のIPv4宛先への変換を行います。

技術的な仕組みとしては、DNS64がIPv4アドレスしか持たないドメインに対してAAAAレコードを合成し、クライアントに返します。クライアントはこの合成されたIPv6アドレスに対して通信を行い、NAT64がその通信を受けてIPv4宛先へ変換します。これにより、IPv6ワークロードからのアウトバウンド通信がIPv4インターネット宛先に到達可能となります。

活用シナリオとしては、Azure上でIPv6のみ対応の仮想マシンやコンテナを運用している場合に、既存のIPv4インターネットサービスと連携する必要がある場合に有効です。また、アプリケーションの移行や新規開発時にIPv6環境を優先しつつ、レガシーなIPv4サービスとの互換性を確保する用途にも適しています。

注意点としては、NAT64の利用にはDNS64対応リゾルバーが必須であること、またNAT64はアウトバウンド通信の変換のみをサポートする点が挙げられます。インバウンド通信や双方向通信には別途対応が必要となる場合があります。また、NAT64の導入により、アプリケーション側でIPv6アドレスの取り扱いやDNS64の設定が求められることがあります。

関連するAzureサービスとしては、StandardV2 NAT Gateway自体が仮想ネットワークのアウトバウンド通信管理を担っており、Azure Virtual Networkや仮想マシン、コンテナサービスなどと連携して利用されます。今回のアップデートにより、これらのサービスでIPv6ワークロードの運用がさらに柔軟かつ実用的になりました。

【注意点】  
既存のIngressリソースとの互換性や移行方法については公式ドキュメントを参照してください。Gateway APIの導入により、設定や運用方法が変わる可能性があるため、事前に十分な検証を行うことを推奨します。

**詳細**:

本アップデートは、「Application Routing with Gateway API」がAzure Kubernetes Service（AKS）において一般提供（GA）となったことを発表するものです。背景として、Kubernetes環境におけるIngressルーティングの管理は、従来の実装と新しいKubernetes標準の両立が求められる状況にあります。これに対応するため、AKS上でKubernetes Gateway APIを利用したアプリケーションルーティングが正式にサポートされることとなりました。

具体的な機能としては、Kubernetes Gateway APIをAKSに統合することで、より柔軟かつ標準化されたIngressルーティングの構成が可能になります。従来のIngressリソースに比べ、Gateway APIはより拡張性が高く、トラフィックルーティングの制御やポリシー管理を細かく行うことができます。これにより、複数のアプリケーションやチームが共存する大規模なKubernetesクラスターにおいても、セキュアかつ効率的なトラフィック管理が実現します。

技術的な仕組みとしては、Gateway APIはKubernetesのカスタムリソース定義（CRD）として実装されており、Gateway、GatewayClass、HTTPRouteなどのリソースを用いてルーティング構成を記述します。AKSでは、このGateway APIをネイティブにサポートすることで、Azure Load BalancerやApplication GatewayなどのAzureネットワークサービスと連携しつつ、Kubernetes標準のAPIを通じてルーティング設定を管理することが可能です。

活用シナリオとしては、マイクロサービスアーキテクチャを採用したアプリケーションの外部公開や、複数のサービスへのトラフィック分岐、TLS終端の一元管理などが挙げられます。たとえば、開発チームごとに異なるGatewayリソースを割り当てて独立したルーティングポリシーを適用することや、複数のドメインやパスごとに異なるバックエンドサービスへルーティングする構成が容易に実現できます。

注意点としては、Gateway APIのリソースや仕様は従来のIngressリソースと異なるため、既存のIngressコントローラーからの移行時には設定の見直しや互換性の確認が必要です。また、AKS上でのGateway API利用に際しては、Azure側でサポートされるGatewayClassやネットワークインフラの制約事項を事前に確認することが重要です。

関連するAzureサービスとの連携については、AKS上のGateway APIがAzure Load BalancerやApplication Gatewayなどのネットワークサービスと統合されているため、Azureのセキュリティ機能やスケーラビリティを活用しつつ、Kubernetesネイティブなルーティング管理が実現します。これにより、Azureのエコシステム全体と連携したモダンなアプリケーションデプロイメントが可能となります。

### 5. Public Preview: Maximum allowed failures for update runs in Azure Kubernetes Fleet Manager 

**公開日時**: 2026年07月28日 16:51:04 UTC
**リンク**: [Public Preview: Maximum allowed failures for update runs in Azure Kubernetes Fleet Manager ](https://azure.microsoft.com/updates?id=567939)

**アップデートID**: 567939
**情報源**: Azure Updates API

**カテゴリ**: In preview, Containers, Azure Kubernetes Fleet Manager, Feature

**要約**:

- 何が更新されたか  
Azure Kubernetes Fleet Managerにおいて、アップデート実行時の最大許容失敗数を設定できる機能がパブリックプレビューとして追加されました。

- 主な変更点や新機能  
アップデートのロールアウト時に「fail-fast」方式を採用している場合、メンバークラスタの一部でアップデートが失敗すると全体のアップデートが停止してしまう課題がありました。今回の新機能により、アップデート実行時に許容できる失敗数の上限を設定できるオプションが追加され、より柔軟なアップデート管理が可能になりました。

- 影響を受ける対象  
Azure Kubernetes Fleet Managerを利用している技術者や運用担当者が対象です。特に複数クラスタを一括で管理・アップデートしている環境に影響があります。

- 注意点があれば記載  
本機能はパブリックプレビュー段階のため、商用環境での利用には注意が必要です。設定値の選定や運用時の失敗検知・対応について、十分な検証を行うことを推奨します。

**詳細**:

Azure Kubernetes Fleet Managerにおいて、「Maximum Allowed Failures for update runs」機能がパブリックプレビューとして提供開始されました。本機能は、Kubernetesクラスタの大規模なフリート（複数クラスタの集合）に対してアップデートを展開する際、失敗が発生した場合の挙動を制御するための新たなオプションです。従来、fail-fast型のアップデートロールアウトでは、少数のメンバークラスタでアップデートが失敗した場合でも、全体のアップデートプロセスが停止し、広範なデプロイメントの進行が阻害されるという課題がありました。

今回のアップデートにより、管理者はアップデート実行時に許容する失敗数の上限値を設定できるようになりました。これにより、設定された閾値を超えない範囲であれば、いくつかのクラスタでアップデートが失敗しても、残りのクラスタへのアップデートを継続することが可能となります。これにより、アップデートの信頼性と柔軟性が向上し、運用効率の最適化が期待できます。

技術的には、Azure Kubernetes Fleet Managerのアップデート実行時に、パラメータとして最大許容失敗数を指定することで動作します。アップデートプロセスは各メンバークラスタの状態を監視し、失敗数が設定値に達した時点で全体のアップデートを停止します。逆に、設定値未満であれば、アップデートは残りのクラスタに対して継続されます。この仕組みにより、アップデートの進行管理がより細やかに制御できるようになります。

活用シナリオとしては、複数のKubernetesクラスタを一元的に管理し、同時にアップデートを適用する大規模な環境で有効です。例えば、地理的に分散した複数のクラスタを運用している場合や、段階的なロールアウト戦略を採用しているケースで、個別の障害により全体のアップデートが中断されるリスクを低減できます。

注意点として、本機能は現在パブリックプレビュー段階であるため、本番環境での利用には慎重な検討が必要です。また、設定した最大許容失敗数を超えた場合にはアップデートが停止するため、アップデート失敗時のリカバリ手順や監視体制の整備が重要です。

本機能はAzure Kubernetes Fleet Managerのアップデート管理機能の一部として提供されており、他のAzure Kubernetes関連サービス（例：Azure Kubernetes ServiceやAzure Monitorなど）と組み合わせて利用することで、より堅牢な運用体制を構築できます。詳細は公式ドキュメントやアップデート情報を参照してください。
